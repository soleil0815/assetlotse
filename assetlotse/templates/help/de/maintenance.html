Updates und Notfallbefehle laufen auf dem Server, im Ordner mit der docker-compose.yml. Dort liegen nur docker-compose.yml, .env (eigene Werte wie Port und Zeitzone, Variablen ASSETLOTSE_*) und der Ordner ./data – das Programm selbst steckt im Image. Updates ändern nie .env, ./data oder docker-compose.override.yml.

Update: Die docker-compose.yml folgt dem Tag latest (neueste Version mit den wöchentlichen Sicherheitsupdates). Updates also mit einer Container-Verwaltung wie Dockhand oder Watchtower (am besten nachts) oder von Hand:

docker compose pull && docker compose up -d

Oder mit ./update.sh: Es merkt sich das laufende Image, lädt die neue Version, startet sie und wartet auf den Gesundheitscheck; startet sie nicht, bietet es an, die vorige wieder zu starten (-y: ohne Rückfrage, später: ./update.sh --rollback). Weitere Möglichkeiten: --version 2.0.0 (Version festlegen, auch zum Zurückgehen), --offline DATEI (ohne Internet, Image-Datei aus dem Release), --cleanup (Programmdateien alter Installationen aufräumen), --help.

Beim ersten Start einer neuen Version sichert AssetLotse die Datenbank selbst (…-vor-<Version>.db, die drei neuesten bleiben immer erhalten) und passt sie erst danach an – egal auf welchem Weg das Update kam. Braucht eine neue Version eine neuere docker-compose.yml, steht oben auf der Seite ein Hinweis: dann ./update.sh ausführen (legt die neue Datei ab, die alte bleibt als docker-compose.yml.alt) oder die Datei aus dem Release übernehmen.

Zurück auf eine ältere Version: Eine ältere Version startet nicht auf einer Datenbank, die eine neuere schon angepasst hat, und nennt im Protokoll (docker compose logs assetlotse) die Sicherung, die zurückzuspielen ist:

docker compose stop assetlotse
docker compose run --rm assetlotse backups
docker compose run --rm assetlotse restore NAME-DER-SICHERUNG.db
# in .env die ältere Version eintragen, z. B. ASSETLOTSE_TAG=2.0.0
docker compose up -d

Umzug auf einen neuen Server: Immer den ganzen Ordner ./data mitnehmen – Datenbank und secret_key gehören zusammen. Ohne die passende secret_key sind 2FA, SMTP-/AD-Passwörter und die vertraulichen Angaben der Gegenstände unlesbar.

Sicherheitsupdates des Images: Basis-Image (Version und Prüfsumme), alle Debian-Pakete und alle Python-Pakete sind auf exakte Versionen festgelegt – jeder Bau ergibt dasselbe Image; Paketverwaltungen wie pip sind im fertigen Image nicht enthalten. Jeden Montag holt GitHub die neuesten Versionen innerhalb des Unterbaus (gleiche Debian-Version, gleiche Python-Reihe, jedes Paket innerhalb seiner Hauptversion), baut neu für amd64 und arm64, lässt die Tests im Image laufen und prüft mit Trivy. Nur wenn alles bestanden ist, erscheint das Image als latest und als <Version>-s<Zähler> (z. B. 2.0.0-s1: gleiches Programm, nur neue Pakete; die geänderten Pakete stehen im CHANGELOG). Server, die latest folgen, bekommen es von selbst. Zusätzlich wird das veröffentlichte Image täglich auf neu bekannte Schwachstellen geprüft, und montags meldet ein Hinweis, wenn Debian oder Python in weniger als 12 Monaten keine Sicherheitsupdates mehr bekommen (rot ab 6 Monaten). Einen neuen Unterbau hebt niemand still an – das ist immer eine bewusste neue Version.

Wenn ein Lauf auf GitHub rot ist (GitHub schickt eine E-Mail): Es wurde nichts veröffentlicht, die Server behalten ihre Version. Die Ursache steht kurz am Lauf. Meist: Tests failed – ein neues Paket passt nicht, Anpassung als neue Version; Trivy … finding(s) – die Korrektur liegt außerhalb der Grenzen (bewusst anheben) oder der Befund ist nachweislich harmlos (Eintrag mit Begründung und Ablaufdatum in .trivyignore); Base ends soon – Wechsel auf den nächsten Unterbau planen; Netzwerkfehler – Lauf erneut starten. Die vollständige Übersicht steht in der README, Abschnitt „Sicherheit und Aktualität des Images“.

Befehle für den Notfall – jeweils mit docker compose exec assetlotse docker-entrypoint.sh davor (über den Entrypoint laufen sie wie die App ohne Root-Rechte, z. B. gehören Sicherungen dann nicht root):

  • flask --app wsgi reset-password admin – neues Passwort für ein lokales Konto (aktiviert es auch wieder)
  • flask --app wsgi reset-2fa admin – zweiten Faktor zurücksetzen
  • flask --app wsgi create-admin notfall – zusätzliches lokales Admin-Konto
  • flask --app wsgi backup – jetzt sichern
  • flask --app wsgi send-reminders – Erinnerungen jetzt versenden
  • flask --app wsgi apply-retention – Aufbewahrungsfrist jetzt anwenden

Fast alles davon geht auch in der Oberfläche: 2FA zurücksetzen und Anmeldesperre aufheben im Benutzerkonto, Jetzt sichern, Jetzt versenden, Jetzt bereinigen. Die Version steht unten in der Seitenleiste; ein Klick darauf zeigt Lizenz und Quellcode.

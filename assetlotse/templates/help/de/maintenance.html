Updates und Notfallbefehle laufen auf dem Server, im Ordner mit der docker-compose.yml. Eigene Werte (Port, Zeitzone …) stehen in .env (Variablen ASSETLOTSE_*); sie wird bei Updates nie überschrieben, ebenso wenig ./data und docker-compose.override.yml.

Update mit update.sh:

./update.sh                        # aktuellen Stand neu bauen und starten
./update.sh assetlotse-X.Y.Z.zip    # neues Paket einspielen, bauen, starten

Das Skript prüft das Paket, legt eine Datensicherung an, tauscht erst dann die Programmdateien aus (bei einem Fehler werden die bisherigen wiederhergestellt), baut das Image assetlotse:VERSION (schlägt das fehl, läuft der alte Container weiter), startet neu und wartet, bis der Container gesund ist. Optionen: --no-backup, --no-cache, --prune (auch das vorige Image löschen), --no-cleanup (nicht aufräumen), --cleanup (nur aufräumen), --pull (fertiges Image von GitHub statt lokal bauen; danach folgt der Container latest, sodass auch andere Update-Tools neue Versionen einspielen können; --version X.Y.Z legt eine Version fest), -y (keine Rückfragen), --help. Beim ersten Start einer neuen Version sichert AssetLotse die Datenbank selbst – auch bei einem Update über ein anderes Tool. Aufräumen: Nach einem erfolgreichen Update kommt das Zip ins Archiv packages/ (aktuelles und voriges Paket bleiben, ältere werden gelöscht); lose Zips, Reste abgebrochener Updates und ältere AssetLotse-Images werden entfernt. Andere Docker-Images bleiben unberührt. Zurück zur vorigen Version: ./update.sh packages/assetlotse-ALT.zip. Nötig sind Docker Compose (Plugin docker compose oder das ältere docker-compose, jede Version) und unzip. Die Datenbank wird beim Start automatisch angepasst.

Umzug auf einen neuen Server: Immer den ganzen Ordner ./data mitnehmen – Datenbank und secret_key gehören zusammen. Ohne die passende secret_key sind 2FA, SMTP-/AD-Passwörter und die vertraulichen Angaben der Gegenstände unlesbar.

Sicherheitsupdates des Images: Basis-Image (Version und Prüfsumme), alle Debian-Pakete und alle Python-Pakete sind auf exakte Versionen festgelegt – jeder Bau ergibt dasselbe Image; Paketverwaltungen wie pip sind im fertigen Image nicht enthalten. Jeden Montag holt GitHub die neuesten Versionen innerhalb des Unterbaus (gleiche Debian-Version, gleiche Python-Reihe, jedes Paket innerhalb seiner Hauptversion), baut neu, lässt die Tests im Image laufen und prüft mit Trivy. Nur wenn alles bestanden ist, erscheint das Image als latest und als <Version>-s<Zähler> (z. B. 1.10.0-s1: gleiches Programm, nur neue Pakete; die geänderten Pakete stehen im CHANGELOG). Server, die latest folgen, bekommen es von selbst. Zusätzlich wird das veröffentlichte Image täglich auf neu bekannte Schwachstellen geprüft, und montags meldet ein Hinweis, wenn Debian oder Python in weniger als 12 Monaten keine Sicherheitsupdates mehr bekommen (rot ab 6 Monaten). Einen neuen Unterbau hebt niemand still an – das ist immer eine bewusste neue Version.

Wenn ein Lauf auf GitHub rot ist (GitHub schickt eine E-Mail): Es wurde nichts veröffentlicht, die Server behalten ihre Version. Die Ursache steht kurz am Lauf. Meist: Tests failed – ein neues Paket passt nicht, Anpassung als neue Version; Trivy … finding(s) – die Korrektur liegt außerhalb der Grenzen (bewusst anheben) oder der Befund ist nachweislich harmlos (Eintrag mit Begründung und Ablaufdatum in .trivyignore); Base ends soon – Wechsel auf den nächsten Unterbau planen; Netzwerkfehler – Lauf erneut starten. Die vollständige Übersicht steht in der README, Abschnitt „Sicherheit und Aktualität des Images“.

Befehle für den Notfall – jeweils mit docker compose exec assetlotse docker-entrypoint.sh davor (über den Entrypoint laufen sie wie die App ohne Root-Rechte, z. B. gehören Sicherungen dann nicht root):

  • flask --app wsgi reset-password admin – neues Passwort für ein lokales Konto (aktiviert es auch wieder)
  • flask --app wsgi reset-2fa admin – zweiten Faktor zurücksetzen
  • flask --app wsgi create-admin notfall – zusätzliches lokales Admin-Konto
  • flask --app wsgi backup / list-backups – sichern bzw. Sicherungen anzeigen
  • flask --app wsgi send-reminders – Erinnerungen jetzt versenden
  • flask --app wsgi apply-retention – Aufbewahrungsfrist jetzt anwenden

Fast alles davon geht auch in der Oberfläche: 2FA zurücksetzen und Anmeldesperre aufheben im Benutzerkonto, Jetzt sichern, Jetzt versenden, Jetzt bereinigen. Die Version steht unten in der Seitenleiste; ein Klick darauf zeigt Lizenz und Quellcode.

Updates and emergency commands run on the server, in the folder containing docker-compose.yml. It only holds docker-compose.yml, .env (your own values such as port and time zone, variables ASSETLOTSE_*) and the folder ./data – the program itself is inside the image. Updates never change .env, ./data or docker-compose.override.yml.

Updates: docker-compose.yml follows the tag latest (newest version with the weekly security updates). So update with a container manager such as Dockhand or Watchtower (preferably at night) or by hand:

docker compose pull && docker compose up -d

Or with ./update.sh: it remembers the running image, pulls the new version, starts it and waits for the health check; if it does not start, it offers to start the previous one again (-y: without asking, later: ./update.sh --rollback). More: --version 2.0.0 (pin a version, also to go back), --offline FILE (without internet, image file from the release), --cleanup (clean up program files of old installations), --help.

When a new version starts for the first time, AssetLotse backs up the database itself (…-vor-<version>.db, the three newest are always kept) and only then adapts it – whichever way the update came. If a new version needs a newer docker-compose.yml, a notice appears at the top of the page: then run ./update.sh (puts the new file in place, the old one stays as docker-compose.yml.alt) or take the file from the release.

Going back to an older version: an older version does not start on a database a newer one has already adapted, and names the backup to restore in the log (docker compose logs assetlotse):

docker compose stop assetlotse
docker compose run --rm assetlotse backups
docker compose run --rm assetlotse restore NAME-OF-THE-BACKUP.db
# put the older version into .env, e.g. ASSETLOTSE_TAG=2.0.0
docker compose up -d

Moving to a new server: always take the whole ./data folder – the database and secret_key belong together. Without the matching secret_key, 2FA, SMTP/AD passwords and the items' confidential details are unreadable.

Security updates of the image: the base image (version and checksum), all Debian packages and all Python packages are pinned to exact versions – every build gives the same image; package managers such as pip are not part of the finished image. Every Monday GitHub fetches the newest versions within the base (same Debian release, same Python line, every package within its major version), rebuilds for amd64 and arm64, runs the tests in the image and scans it with Trivy. Only if everything passed is the image published as latest and as <version>-s<counter> (e.g. 2.0.0-s1: same program, only new packages; the changed packages are listed in the CHANGELOG). Servers following latest get it by themselves. In addition the published image is scanned every day for newly known vulnerabilities, and on Mondays a note appears when Debian or Python will stop getting security updates within 12 months (red from 6 months). Nobody raises the base silently – that is always a deliberate new version.

When a run on GitHub is red (GitHub sends an e-mail): nothing was published, the servers keep their version. The cause is shown briefly on the run. Usually: Tests failed – a new package does not fit, the fix comes as a new version; Trivy … finding(s) – the fix lies outside the limits (raise it deliberately) or the finding is provably harmless (entry with reason and expiry date in .trivyignore); Base ends soon – plan the switch to the next base; network errors – run it again. The full overview is in the README, section "Security and freshness of the image".

Emergency commands – each prefixed with docker compose exec assetlotse docker-entrypoint.sh (going through the entrypoint runs them without root rights like the app, so e.g. backups are not owned by root):

  • flask --app wsgi reset-password admin – new password for a local account (also re-enables it)
  • flask --app wsgi reset-2fa admin – reset the second factor
  • flask --app wsgi create-admin emergency – additional local admin account
  • flask --app wsgi backup – back up now
  • flask --app wsgi send-reminders – send reminders now
  • flask --app wsgi apply-retention – apply the retention period now

Most of this is also available in the interface: reset 2FA and lift sign-in locks in the user's account, Back up now, Send now, Clean up now. The version is shown at the bottom of the sidebar; clicking it shows the licence and source code.
